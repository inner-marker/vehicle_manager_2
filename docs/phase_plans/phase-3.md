# Phase 3: Local-first & sync (plan)

*Agreed 2026-11-08 · Roadmap: `docs/plan.md` §9 Phase 3 · Open questions: settled (decisions #071, #072) · Security: `docs/sub-plans/04-security.md`*

**Goal:** the **desktop app works offline.** It keeps an encrypted copy of the household's data on the computer, logs fuel-ups, readings, jobs, and photos with no connection, and syncs when it's back on the tailnet. A lost laptop can be locked and signed out, and a damaged or reset server can never damage the desktop's copy.

**Who it's for:** the desktop app only. The web app stays online-only (#071), and the phone apps are post-MVP (#041); they'll reuse this phase's sync engine unchanged.

**Not in Phase 3:** what's due and fuel economy (Phase 5); custom roles, API-wide rate limits, and the internet-facing guide (Phase 6, #071); server-side encryption (Phase 7, #071); the phone apps (post-MVP).

**Exit criteria:**
- **Offline logging:** on the laptop, with Wi-Fi off, log a fuel-up with a photo. Turn Wi-Fi on: within a minute it's on the web, photo and all.
- **Edits merge:** edit one draft on the web and on the laptop (offline) in different fields; after syncing, both edits are kept. The same field: the later edit wins, by its clock (#043).
- **A rejected change is never lost:** an offline reading lower than one synced meanwhile shows in Messages to resolve; nothing is dropped.
- **A lost laptop:** signed out from **Settings → Devices** on the web, it can't sync, and a copied token is refused. Its local data stays encrypted, and the app is locked by its PIN.
- **Loss detection:** restore the server from an old snapshot; the laptop goes into **protective mode**, loses nothing, and can rebuild the server from its copy.
- **Old and new apps:** an app one API version behind still syncs; two behind is told to update and keeps its unsent changes.

**How this file works:** the same as `phase-2.md` (decision #021).
- One branch and **one PR into `dev` per milestone** (`milestone/p3-mN-<slug>`), merged with a merge commit.
- Each **step** is one Conventional Commit. Steps are planned in detail, and approved, when their milestone starts.
- Screens get **SVG layout options** in `docs/ui-sketches/` before they're built (#040).
- Each milestone has a test plan in `docs/test-plans/`, run on the test server (#062) with the desktop app.
- `cargo clean` at each step's end, once its checks have run (the human's disk is small).
- Status: ⬜ not started · 📝 planning · 🔨 in progress · ☑️ committed on the milestone branch · ✅ in `dev`.

## Why this order

- **1 first:** the icon and the exact build were asked for before more desktop use, and every later test plan can then confirm its image from the app. Secret types come before the desktop starts storing secrets, and the spike settles the encrypted database before milestone 4 depends on it.
- **2 before 3:** the PIN unlocks the device's key, so the key (pairing) comes first.
- **3 before 4:** the local database's key is wrapped by the PIN, so the lock exists before there's data to lock.
- **4 before 5:** reading locally (pull) is simpler and proves the data layer; writing (push) builds on it.
- **6 after 5:** a file added offline is uploaded before the change that uses it, so it needs the outbox.
- **7 last, but before the release:** loss detection guards the desktop's copy against a damaged server, which only matters once that copy exists; it ships with sync, never after (plan §9).

## To decide when each milestone is planned

- **Milestone 1:** the icon's design (SVG options first, #040); where the build information comes from outside CI (a `build.rs` reading `git`, or "local build").
- **Milestone 2:** how the request signature is formed (DPoP's JWT form, or a smaller one of our own); how long a signature is valid; what Settings → Devices shows for a browser session.
- **Milestone 4:** the shape of the data layer (one trait with a server and a local implementation, or per-screen functions); how a first download shows its progress; how the desktop's storage crate is gated so the web build never pulls in sqlx (plan §3).
- **Milestone 5:** what Messages offers for each kind of rejected change; how long the outbox may grow before the app warns.
- **Milestone 7:** the thresholds for "suspicious"; how "rebuild the server" proves the device's copy is complete.
- **Draft sub-plans that touch Phase 3:** signatures and records (`01`: the device key from milestone 2 is the one it later certifies), and security (`04`, confirmed: §4, §6, §7.1, §7.4 land here). Each is raised before the milestone it affects.
- **Open issues** are reviewed with each milestone's plan (AGENTS.md); #24 and #26 stay open for a later phase.

**Step 1c notes (2026-11-08):**
- **`domain::build_info::BuildInfo`:** the commit (shortened to 7), "modified", the image tag, and the build date; each optional, and an odd value (not hexadecimal, characters Docker tags don't allow, too long) is dropped rather than shown. One line: `dev · a885ac6 · 2026-11-08 19:02 UTC`, or `local build · a885ac6 · uncommitted changes`.
- **Where the values come from:** `server-image.yml` passes `BUILD_COMMIT` (the workflow's commit), `BUILD_TAG` (metadata-action's `version`: the branch's tag, or a release's version), and `BUILD_DATE`; the `Dockerfile` hands them to `dx bundle` as `VEHICLEMANAGER_BUILD_*`, declared just before that step. A local build's `crates/app/build.rs` asks `git` for the commit and uncommitted changes (rechecked when a commit is made or something is staged). Inside Docker there's no `.git`, so the image relies on the arguments. `deploy_config.rs` checks the workflow, the `Dockerfile`, and the names agree.
- **What shows:** Diagnostics → About gains **Build** (this app's own; the web app and its server share one, being built together) and **Server** (its version and build: always on the desktop, and on the web only when the server has moved on since the page loaded). The handshake carries the server's build (an optional field, so older apps ignore it), and the server's "app starting" log line names it too.

**Step 1d notes (2026-11-08):**
- **`domain::secret::Secret` instead of `secrecy`:** Dioxus sends server-function arguments as JSON both ways, and `secrecy`'s `SecretString` deliberately can't be serialized. `Secret` is a small type of our own: `Debug` prints `[redacted]`, there's no `Display`, the text is reached only through `.expose()`, and on the wire it's a plain string (`serde(transparent)`), so the API didn't change. Unlike `secrecy`, it doesn't wipe its memory when dropped (that needs a dependency or `unsafe`); the risk here is logs. No new dependency.
- **Where it's used:** every password, code, and token parameter of the server functions (sign-in, setup, the setup-code check, password change, Admin mode, recovery), the matching `server` functions down to hashing, the tokens and temporary passwords in the answers (`SignInOutcome`, `SetupOutcome`, `RecoveryOutcome`, `UserAdminOutcome`), and the desktop's in-memory token.
- **The rule** is in AGENTS.md ("What logs may contain"): no secrets or record text at any level; IDs, not contents; the setup and recovery codes only with `console_only = true` (never the log files or the in-app viewer); what each level is for.
- **`crates/server/tests/secrets_in_logs.rs`** runs setup, sign-in, a wrong password, Admin mode, a password change, adding a user, a password reset, and a recovery at trace level, and fails if any secret reaches the log or a code appears in a line that isn't console-only. Checked by logging a password on purpose: the test failed.

**Step 1e notes (2026-11-08):**
- **`spikes/sqlcipher/`** is its own workspace with its own `Cargo.lock` (and ignored by Docker), so its SQLCipher build of `libsqlite3-sys` can never mix into the server's plain SQLite through Cargo's feature unification. It uses the app's sqlx (0.9.0, `sqlite-bundled`), and chooses SQLCipher through the same `libsqlite3-sys` (0.37.0) with one of two features: **system crypto** (`bundled-sqlcipher`: Apple's CommonCrypto on macOS, the system OpenSSL elsewhere) or **bundled OpenSSL** (`bundled-sqlcipher-vendored-openssl`).
- **Seven checks:** it's SQLCipher (`PRAGMA cipher_version`); create and write; the file has no plain SQLite header and the text isn't visible in it; the right key reads; a wrong key and no key are refused ("file is not a database"); `PRAGMA rekey` keeps the data and retires the old key. sqlx sends the `key` pragma before anything else by design (`sqlx-sqlite` 0.9.0, `options/mod.rs`).
- **macOS (local, Apple Silicon, release builds from clean):**

  | Build | Time | Binary | Checks |
  |---|---|---|---|
  | Plain SQLite | 16.6 s | 3.0 MB | (not run) |
  | SQLCipher, Apple's crypto | 18.2 s | 3.1 MB | 7 of 7 |
  | SQLCipher, bundled OpenSSL | 42.7 s | 6.7 MB | 7 of 7 |

- **All three platforms** (`.github/workflows/sqlcipher-spike.yml`, run 2026-11-09 on GitHub's runners; cold builds, including downloading crates; it runs when the spike changes, or by hand once it's on `dev`):

  | | Plain SQLite | SQLCipher, system crypto | SQLCipher, bundled OpenSSL |
  |---|---|---|---|
  | **Linux** | 72 s, 3.4 MB | 74 s, 3.5 MB, 7 of 7 | 124 s, 8.3 MB, 7 of 7 |
  | **macOS** | 78 s, 2.9 MB | 31 s, 2.9 MB, 7 of 7 | 142 s, 6.4 MB, 7 of 7 |
  | **Windows** | 90 s, 2.4 MB | 86 s, 2.5 MB, 7 of 7 | 594 s, 6.5 MB, 7 of 7 |

- **What Windows needed** (the first run's two Windows SQLCipher builds failed on the build machine, not on SQLCipher): system crypto needs OpenSSL installed and named (`OPENSSL_LIB_DIR`, `OPENSSL_INCLUDE_DIR`; the runner's keeps `libcrypto.lib` in `lib\VC\x64\MD`), and the program then needs OpenSSL's DLLs to run, so a Windows package would have to ship them. Bundled OpenSSL needs the full Strawberry Perl (`OPENSSL_SRC_PERL`), not Git's minimal one, and takes about 10 minutes to build in CI.
- **Recommendation for milestone 4** (to settle when it's planned): **macOS: system crypto** (Apple's CommonCrypto, part of the OS, almost no cost); **Windows: bundled OpenSSL** (self-contained: no DLLs to ship or keep patched; the slow build only hits CI and Windows developers); **Linux: system crypto** (OpenSSL is on every desktop distribution, and `.deb` and `.rpm` packages can name it as a dependency), or bundled if a self-contained binary matters more than 5 MB. Cargo can choose per platform: an optional `libsqlite3-sys` with different SQLCipher features in `[target.'cfg(...)'.dependencies]` tables, switched on only by the desktop build, so the server (and its Linux image) keeps plain SQLite until Phase 7.
- **Not tested yet (for Phase 7):** that a SQLCipher build opens an existing plain database with no key (SQLCipher documents that it does), and SQLCipher's `sqlcipher_export` for encrypting an existing database in place.

**Step 2a notes (2026-11-09):**
- **Migration 0016:** the `devices` table (its `kind` is plain text checked by `domain::device::DeviceKind`, so a kind can be added without a rebuild; `name` is empty until there is one); each existing session gets a device of its own, recorded as an unnamed browser (today's desktop sessions can't be told apart, and end within 30 idle days); `sessions` is rebuilt so its device must exist. The fixture test now also checks foreign keys, and that every migrated session's device can be read.
- **A device is "signed in" while it has a session that hasn't ended** and hasn't been signed out; the list needs no clean-up job. Signing a device out ends its sessions and stamps it once; the row stays (changes carry its ID). A session's use also updates its device's "last seen".
- **Every sign-in now stores a device** with its session, in one transaction: a browser until 2c pairs desktops.

**Step 2b notes (2026-11-09):**
- **Changed from the plan, with the human's choice:** Dioxus 0.7.10 sends server-function calls with one shared set of extra headers (`set_request_headers`) and has no per-request hook, so those calls can't be signed per request. One format, two scopes (`domain::device_signature`): **request** (method, path and query, time, nonce, token hash; within 5 minutes and accepted once) for the app's own requests (files now, sync from milestone 5), and **session** (no method or path; within 2 minutes, reusable, renewed every 30 seconds) in the shared headers for server-function calls. A copied token alone is refused either way; a captured session signature works only briefly (and capturing it means breaking HTTPS).
- **Header:** `x-device-signature: v1;scope=request;t=<ms>;n=<32 hex>;s=<128 hex>`; Ed25519 (`ed25519-dalek` 3.0.0, same SHA-2 as the workspace, builds for the browser too) over a fixed label, the scope, method, path, time, nonce, and the token's SHA-256 (`domain::device_signature::token_hash`, which the server's `token_hash` now uses).
- **Server:** `sessions::resolve_signed` checks a keyed device's signature **before anything is written** (a copied token can't even keep a session alive); plain `resolve` never lets a keyed device in. The auth layer refuses a bad signature with the new `ApiError::DeviceSignature` (401), except on a public path, which goes on as signed out. Request nonces are remembered in memory for twice the window.
- **Tests** (`crates/server/tests/device_signatures.rs`, through the real auth layer): request and session signatures pass; no signature, a replay, another path, an old time, another device's key, and a malformed header are refused; a public path without one goes on as signed out; a refused request writes nothing.

**Step 2c notes (2026-11-09):**
- **API version 2** (the server still accepts 1). The sign-in server function takes an optional `Pairing` (the public key as hex, and a name); `server::sessions::sign_in_from` stores the device as a **desktop with its key and name**, an **older desktop** (a version-1 app asking for a token: no key, "Desktop app (older version)"), or a **browser**. A desktop the server no longer accepts (signed out elsewhere) forgets its pairing.
- **Checked end to end** against a local server: pairing over HTTP stored a desktop device with its key; with the token alone a protected call was refused (`device-signature`) and the session check said signed out; signed, both worked. ### Milestone 3 plan: app lock and PIN

*Agreed 2026-11-11 · branch `milestone/p3-m3-app-lock` · sketch: `docs/ui-sketches/p3m3-lock-options.svg` (1B, 2B, 3A) · decision #074 · sub-plan 04 §4.1*

**Choices (the human, 2026-11-11):**
- **The PIN encrypts the stored sign-in:** the desktop's device key and token are kept encrypted with a key made from the PIN (Argon2id, then XChaCha20-Poly1305), in the keychain (or the file in debug builds); a copied item or file is useless without it. Milestone 4's database key is wrapped the same way.
- **The password unlocks offline too:** the same sign-in is also encrypted with a key made from the password. After the password is changed elsewhere, the old one keeps unlocking this computer until its next sign-in.
- **It locks at launch and when idle:** after 15 idle minutes by default (5, 15, 30, or 60 minutes, or only when the app opens; per computer).
- **A PIN is required:** right after pairing, the desktop asks for a new one (twice) before showing the app.
- **Sketch:** **1B** (choose a PIN with dots and a keypad; the keyboard works too), **2B** (locked: the full window, dots and a keypad; "Use your password instead" and "Sign out" below), **3A** (Lock after and Change PIN under Settings → You → This device).
- **Rules:** 6 digits or more; no repeats (`111111`) or runs (`123456`, `654321`). The sub-plan's "not your birth year" is dropped: the app doesn't know anyone's birth year.
- **Wrong tries:** after 5 wrong PINs only the password works; after 10 wrong tries in all, the desktop signs out and forgets its sign-in. The count is kept beside the encrypted sign-in; someone with a copy of the file could try PINs without that limit, each try costing an Argon2 hash (and, in release builds, the keychain stands in the way first).
- **Failed unlocks are reported:** the desktop tells the server when it's next unlocked; the household Admin sees it in Messages. (Not before forgetting itself after 10 wrong tries: its token is sealed behind the PIN that was never entered, so it can't make a signed request. See step 3d's notes.)
- **Desktops paired in milestone 2** (unencrypted sign-in) sign in once more after the update, then choose a PIN.

**New dependency (approved with this plan):** `chacha20poly1305` (RustCrypto). `argon2` is already in the workspace.

**Step 3b notes (2026-11-11):**
- **`app::sealed::SealedCredential`:** two sealed copies of the key and token (one for the PIN, one for the password), each with its own 16-byte salt and 24-byte nonce; Argon2id (**256 MiB, 3 passes**: about 0.3 s per unlock on an M-series Mac, measured) then XChaCha20-Poly1305 (`chacha20poly1305` 0.11) with the server's address as associated data, so a sealed sign-in can't be moved to another server's entry. The wrong-try count sits beside the seals. Changing the PIN reseals the PIN's copy and clears the count; the password's copy stays.
- **At that cost,** trying every 6-digit PIN on a copied file takes days on one core, and each try needs 256 MiB. 64 MiB (67 ms) was measured first and judged too light.
- **Debug builds** compile `argon2` and `blake2` optimized (`[profile.dev.package]` in the workspace `Cargo.toml`): unoptimized, an unlock took about 5 s. The server's password checks in debug builds get faster too.
- **`device_credential` stores only the sealed form** (keychain, or the file in debug builds). A pairing stored unsealed in milestone 2 is recognized, removed, and the desktop signs in once more.
- **Between 3b and 3c** the desktop doesn't stay signed in across launches: the sealed sign-in is written and opened by the screens in 3c.

**Step 3c notes (2026-11-11):**
- **`ui::lock::LockGate`** stands in front of the whole app on the desktop: **Choose a PIN** right after pairing (the token, key, and the password typed at sign-in wait in memory only until the PIN seals them), and **Locked** at launch (when a sealed sign-in exists) and after the idle time (the idle watcher locks once "Lock after", from `settings.json`, has passed with no input). While locked, the key and token aren't in memory and nothing behind the gate runs.
- **The keypad** (1B, 2B): dots for the digits typed (at least six shown), keys 1–9, ✓, 0, ⌫; the keyboard works too (digits, Backspace, Enter). A PIN is typed, then typed again; a rule broken or a mismatch says why.

"Sign out of this computer" forgets it at once. Unlocking runs Argon2 on a blocking thread (the desktop's tokio gains its `rt` feature).
- **The lock screen says whose it is:** the person's display name is kept beside the seals (not sealed; it says only whose computer this is), with the server's host.
- **Not seen in this session:** the desktop's webview can't be driven or captured here (no Screen Recording permission), so the screens are checked by the test plan; the app starts cleanly with the gate in place.

**Step 3d notes (2026-11-11):**

It reports when it's next **unlocked**: how many wrong tries came before, and when the last was. **Step 3e notes (2026-11-11):**
- **Where:** two rows under Settings → **This device**, after Theme and Keep window on top, on a desktop with a sealed sign-in only (`ui::lock::LockSettings`). They show on every tab but Devices, like the other This device rows.

- **Change PIN** opens a small form under the row: the current PIN (or "Use your password instead"), the new PIN, and the new PIN again. The new PIN's rules and the match are checked first, so a typo there costs no try. A wrong current PIN or password counts as a wrong unlock (it's the same check): after 5 wrong PINs the form asks for the password, and the 10th wrong try signs the desktop out as the lock screen does. ### Milestone 5 plan: outbox and push

*Agreed 2026-11-12 · branch `milestone/p3-m5-outbox` (from `dev`) · sketch: `docs/ui-sketches/p3m5-outbox-options.svg` (1A, 2A, 3B) · decision #076 · #005, #043, #072, #075*

**Choices (the human, 2026-11-12):**
- **Offline, a person can make every change Driver mode allows them online:** log, edit, finish, and correct events (the kinds their role lets them log); open, edit, and remove squawks (and sign off or defer them, if their role allows); their own preferences, saved places, and garage order. Admin work (vehicles, meters, fields, groups, documents, plates, references, schedules, users, devices) stays online-only; it needs Admin mode, which needs the server. Adding photos and PDFs offline is milestone 6.
- **A change the server refuses** goes to Messages on that desktop, saying what and why, with **Open** (back in its form, as typed, to fix and save again) and **Discard**. Nothing typed is lost until it's discarded.
- **Waiting changes:** always counted on screen; after **24 hours** unsent, or **100** changes, a message says so and suggests connecting.
- **Signing out with changes waiting** warns: "3 changes haven't been sent", with **Send now** (online), **Cancel**, and **Sign out anyway**. The 10th wrong PIN still signs out without asking (its changes are lost with the copy, as the copy is).
- **Sketch:** **1A** (a blue **↑ 3 to send** chip in the top bar's sync spot, replacing the "Sync not set up" placeholder; its tooltip gives the oldest, and a click opens Diagnostics), **2A** (a refused change is an amber message like the others: what, the server's reason, Open and Discard), **3B** (the sign-out warning lists the waiting changes, a few then "and 5 more", with Send now, Cancel, and Sign out anyway).

**How it works (the design):**
- **A change is an operation:** the same input the screen sends today (`EventInput`, `SquawkInput`, a preferences patch…), plus what the server used to make itself: the **IDs** of new records (UUIDv7, made on the desktop), the desktop's **HLC stamp**, and an **operation ID**. An **edit carries only the fields the person changed** (compared with what the form started from), so a field changed meanwhile on the web isn't overwritten by one the person never touched (#043). `domain::sync::Operation`, versioned (`OPERATION_FORMAT_VERSION = 1`), absolute values, never deltas (#005).
- **The desktop applies it to its copy first**, with the server's own write code (as 4d does for reads), so the same checks run and a mistake shows in the form at once, online or off. The desktop's HLC is kept in the copy and moves past every stamp it pulls.
- **The outbox:** each operation is added to it, in order, just before it's applied to the copy, and taken out again if the copy refuses it (5b notes).
- **Push:** online, an operation is sent at once and the form waits for its answer, as today; if the server can't be reached, it stays in the outbox and the screen moves on. The outbox is pushed **before every pull** (so a pull never covers a change that hasn't been sent), at unlock, every minute while anything waits, and at Send now.
- **On the server:** `POST /api/v1/sync/push` (paired desktops on the same schema, like pull) takes operations in order and **runs each through the same server function as an online save**, with the desktop's IDs and stamp, so everything is checked again: permissions (as the person is now: a role removed meanwhile refuses), domain rules, and the per-field newest-wins merge. **Never applied twice:** the server keeps each operation's ID and outcome (`applied_operations`), and a resent operation gets the same answer. The answer, per operation: **applied**, **already applied**, or **refused** (the reason). After a refusal the desktop empties its copy's records and downloads them again, keeping its outbox, so the copy is as the server has it (5c notes).
- **Acknowledged** operations leave the outbox; **refused** ones stay, marked refused, for Messages (Open or Discard). Later operations still go: each operation stands alone.
- **Versions (#072):** the push names its operation format. The server accepts the current format and the one before (upcasting it); an older app is told to update and keeps its outbox. Format 1 is the first, so there's nothing to upcast yet; the check and its answer are built and tested.
- **A clock far in the future** (more than 5 minutes ahead, as now) is refused, the operation stays in the outbox, the desktop says its clock is wrong, and the device is **flagged** for the Admin (a message, like failed unlocks).
- **Server-set values** stay the server's: who logged it (the session's person), when it was received (the push's time). When it was made comes from the operation.

**Step 5a notes (2026-11-12):**

### Milestone 6 plan: files

*Agreed 2026-11-12 · branch `milestone/p3-m6-files` (from `milestone/p3-m5-outbox`, merged into `dev` in PR #47) · sketch: `docs/ui-sketches/p3m6-files-options.svg` (1A, 2A, 3B) · decision #077 · #036, #037, #065, #072, #075, #076 · sub-plan 04 §7.2*

**Choices (the human, 2026-11-12):**
- **Files on the desktop are kept in a second encrypted database,** `files.sqlite`, beside the copy in its folder and under the same key (SQLCipher, as the copy; no new dependency). It's separate so downloading the copy's records again (5d) doesn't wipe it; it's deleted with the copy at sign-out or the 10th wrong PIN.
- **Disk:** thumbnails and PDFs download by themselves; a photo downloads when opened and is then kept, **up to 2 GB by default** (a setting per computer, on Diagnostics: 1, 2, 5, 10 GB, or no limit). Past it, the photos opened longest ago are dropped and download again if opened. Thumbnails, PDFs, and anything not yet sent are never dropped. Originals only on request, as now.
- **Offline, photos and documents can be added, removed, and moved between a job's tasks.** Originals still need the server.
- **Sketch:** **1A** (offline, a photo whose full size isn't here opens as its thumbnail, enlarged, with "Full size downloads when this computer can reach the server (a small preview)."), **2A** (a photo added offline and not yet uploaded has a small blue **↑** in its tile's corner; tooltip "Waiting to upload (offline)."), **3B** (the limit is set on **Diagnostics → Offline copy**, with the copy's other numbers: files, and photos kept of the limit).

**How it works (the design):**
- **The files database** (`storage::local_files`, its own small schema): each file by its SHA-256, its bytes, what it is (photo, thumbnail, PDF, original, or an upload waiting), its size, when it was last opened, and whether it may be dropped.
- **Reading a file** (`app::files`): the files database first; otherwise, online, the server (as now), then kept; offline and not here, the sketch's row 1. The in-memory cache of the session stays for what's on screen.
- **Downloading by themselves:** after each pull, a background fetcher downloads the thumbnails and PDFs of the copy's attachments that aren't here yet, a few at a time, never while offline.
- **Adding offline:** the photo or PDF is processed on the desktop with the server's own code (the same JPEG and thumbnail, #036), kept in the files database as an upload waiting, and the attachment is saved on the copy at once (an operation, 5a's way). **Sending:** a push first uploads each waiting file the next operations need; the server processes it and answers with its hashes; the operation goes with those (the server's), so the record points at files the server has. The desktop then drops the waiting upload once the server's version is here.
- **Removing and moving** are operations too (`RemoveAttachment`, `MoveAttachment`); the log form's task moves go through the data layer.
- **The server's audit record** (#072): migration 0020 adds who removed an attachment and when (`removed_by`, `removed_ms`), and a table `erased_files` written by the nightly file check when it erases a file: its SHA-256, size, kind, type, name, the attachment and the record it belonged to, who removed it and when, and when it was erased. No content. Not shown anywhere yet (a report can read it later).
- **Keep rule:** an uploaded file is kept 8 days unused on the server (#065); a push uploads a file right before the operation that uses it, so nothing waits between them.

### Milestone 7 plan: loss detection

*Agreed 2026-11-13 · branch `milestone/p3-m7-loss-detection` (from `milestone/p3-m6-files`, which isn't merged yet) · sketch: `docs/ui-sketches/p3m7-loss-detection-options.svg` (1A, 2A, 3B) · decision #078 · plan §6 "Data integrity & loss detection" · #035, #065, #072, #075, #076, #077*

**What the survey found** (why this milestone matters): today a server that was reset or restored from an old snapshot can cost the desktop its data. A server that no longer knows the desktop's sign-in signs it out, which **deletes the copy and its unsent changes**; a changed database ID is accepted silently (an empty copy starts); a server restored from an older snapshot (same ID, lower change numbers) goes unnoticed, and its next changes, numbered below the desktop's cursor, are **skipped for good**; an unhealthy server still serves pulls; and nothing snapshots the copy.

**Choices (the human, 2026-11-13):**
- **A suspicious pull** deletes more than **25 records and more than 10%** of this computer's copy: it waits for a person; nothing is applied.
- **If the server no longer knows this desktop** (it signed the desktop out, or was reset or restored and forgot the pairing), **the copy and its unsent changes are kept** until the person decides: sign in again (the copy carries on), rebuild the server (Admin), or delete the copy. Signing out from the account menu still deletes it (3B's warning first).
- **Snapshots of the copy:** one a day (before its first pull), and always before a risky step (applying a suspicious pull, leaving protective mode, downloading the copy again after a refusal, a rebuild); the **7 newest** kept, encrypted like the copy; restoring one is on Diagnostics.
- **Rebuild the server from this device:** the household **Admin's** desktop only, only with a copy **complete at its last pull and nothing waiting or refused**, with a **typed confirmation**. Everyone keeps their account with a **new temporary password** (shown once to the Admin); other desktops pair again; other people's own settings, saved places, and Garage order start empty.
- **Sketch:** **1A** (protective mode: a red **PROTECTED** tag in the top bar and a red strip under it saying why, with **Details** for the choices, on every screen until settled), **2A** (a suspicious pull: a dialog when it happens, naming what would go, with **Keep this computer's copy** and **Apply them**, which takes a snapshot first), **3B** (rebuild: a step-by-step dialog, from protective mode's Rebuild and from Diagnostics: the checks, what happens, then type REBUILD).
- **Photos never downloaded** (only thumbnails) can't be rebuilt: their attachments are left out and listed (part of the approved plan).

**How it works (the design):**
- **Detecting, on every pull** (the page already carries the server's database ID and newest change number): the **database ID differs** from the copy's (reset, or another server) → protective mode "the server changed"; the server's **newest change number is below the copy's cursor** (restored from an older snapshot) → protective mode "the server went back in time". The server **refuses pulls and pushes while unhealthy** (`PullOutcome::Unhealthy`), and the desktop waits ("the server isn't well"), resuming by itself when it's healthy again. The handshake no longer overwrites a remembered database ID: a different one is the same "the server changed".
- **Protective mode:** no pulls are applied and nothing is pushed; the copy, its files, and its outbox are untouched; the app still reads and saves here (the outbox grows); a sync alert in Messages (this computer's, so it shows offline) and the sketch's row 1. The choices: **keep protected**; **use this server** (a snapshot first, then the copy downloads this server's records again; unsent changes stay to be sent, and are checked there as usual); **rebuild the server from this computer** (Admin); for "signed out", **sign in again** (the copy's key carries over to the new sign-in, so the copy and outbox stay).
- **A suspicious pull:** before applying a page, the desktop counts what it would delete (tombstones and rows marked deleted for records the copy has live). Past the line, the page waits (row 2); **Keep this computer's copy** holds syncing (protective mode until settled), **Apply** takes a snapshot, then applies it. Downloading again after a refusal (5d) is a risky step too: a snapshot first.
- **Snapshots** (`storage`): the copy written to `servers/<id>/snapshots/` encrypted under its key (SQLCipher's `VACUUM INTO`, or `sqlcipher_export` if that doesn't keep it encrypted: a spike in 7a decides), checked, rotated to 7. The files database isn't snapshotted (its files are by hash, and the server has them). **Restore** (Diagnostics): the copy closes, the snapshot takes its place, and it opens; the next pull catches up from its older cursor.
- **Rebuild** (`POST /api/v1/rebuild`): onto a **fresh server** only (no users yet: it shows setup), proved like setup by the server's **setup code** (from its log) plus the Admin's own sign-in on the desktop. The desktop sends its records in pages (the pull's format, the other way), with field clocks and tombstones, so newest-wins carries on; the server applies them in one go (its default group replaced), re-keys the household's settings to its new database ID, gives every person a new temporary password (the Admin chooses their own, as at setup), pairs this desktop, and uploads the files this desktop has. Attachments whose file isn't here (photos never opened) are left out and listed. The desktop then starts a new copy of the rebuilt server (the old one kept as a snapshot), and other desktops see "the server changed" and choose **use this server**.
- **Sync alerts in Messages** (desktop, shown offline too, with the badge): protective mode and why, a pull waiting, the server not well, beside 5e's refused changes.
