# Phase 2: Data model & server storage (plan)

*Agreed 2026-10-29 · Roadmap: `docs/plan.md` §9 Phase 2 · Open questions: none (decisions #028–#041)*

**Goal:** the household can really use the app, online, from the web UI on the NAS (phones and computers) and the macOS desktop app. Vehicles, meters, fuel-ups, readings, maintenance, repairs, squawks, photos, and documents are stored in the server's SQLite database, every change goes through a command, and the data survives restarts, updates, and a bad day (integrity checks and nightly snapshots).

**Not in Phase 2:** offline use and sync (Phase 3), what's due and fuel economy statistics (Phase 5), the mobile apps (post-MVP, #041).

**Exit criteria (proposed):**
- On the NAS, signed in as real users: add the household's vehicles, then log a fuel-up, a reading, a maintenance event with tasks and a squawk sign-off, and a repair, each with a location and photos, from a phone browser and the desktop app.
- Wrong roles are refused (a Driver can't log maintenance), finalized events can only be amended, and a wrong password is rejected cleanly.
- After a container restart and an image update, everything is still there; the nightly snapshot exists and passes its integrity check.

**How this file works:** the same as `phase-1.md` (decision #021).
- One branch and **one PR into `dev` per milestone** (`milestone/p2-mN-<slug>`), merged with a merge commit.
- Each **step** is one Conventional Commit. Steps are planned in detail, and approved, when their milestone starts.
- Screens get **SVG layout options** in `docs/ui-sketches/` before they're built (#040).
- Status: ⬜ not started · 📝 planning · 🔨 in progress · ☑️ committed on the milestone branch · ✅ in `dev`.

## Why this order

- **1 before everything:** every later milestone stores data through the command pipeline and migrations, so they come first, with the safety net (integrity check, snapshots) from day one.
- **2 next:** real users and roles replace the test credential before any real data is entered, so nothing is ever stored without an owner and a permission check.
- **3 early and small:** later milestones send messages (snapshot failures, forgotten jobs), so the inbox exists before they need it.
- **5 before 6:** every event requires a location, so locations exist before the first event.
- **6 before 7:** fuel-ups and readings are the simplest events and prove the spine, finalizing, and amendments; maintenance builds on them.
- **8 and 9 last:** attachments and lifecycle hang off assets and events that already exist.

**Written so far**
- **1a:** `domain::hlc` (`Hlc`, `HlcClock` with `tick`/`receive`, full counter rolls into the next millisecond, wall clocks before 1970 never fail) and `domain::hlc_utils` (`check_not_too_far_ahead`, `MAX_AHEAD_MILLIS` = 5 minutes). Property tests: stamps strictly increase over random clock jumps and incoming stamps; packing round-trips. `Clock` is now implemented for `&T`. Dev-only `proptest` 1.12.
  - **Change from the plan:** the device-ID tiebreak moved to 1b, where `DeviceId` exists.
- **1b:** `domain::id`: `Id<T>` (always `UUIDv7`; text, 16-byte, and JSON forms; `created_at`; `cast`), with `DeviceId` and `DatabaseId`; refuses other UUID versions. `hlc::Stamp` (HLC + device ID, ordered HLC first) is the last-write-wins key. `test_support::test_id(n)` makes repeatable IDs. `uuid` 1.28 with no features (it was already in `Cargo.lock`; the lockfile gains one line).

- **1c:** `storage::Database::open`: creates or opens `<data dir>/vehiclemanager.sqlite` (WAL, `NORMAL` sync, 5 s busy timeout, foreign keys); refuses a newer schema without touching it; backs an existing database up to `<data dir>/backups/pre-migration-<UTC>-v<N>.sqlite` before migrating; runs the embedded migrations; records the database and server device IDs on first open. `0001_init.sql`: `database_meta`, `applied_commands`, `field_clocks`, `tombstones`, `jobs` (all `STRICT`; unreleased until `v0.2.0`, so it may still change). `storage::convert` for ID and HLC columns. `domain::time_utils::format_utc_file_stamp` for file names. The migration fixture test and `tests/fixtures/README.md` (first fixture at `v0.2.0`; `.gitignore` lets fixtures in).
  - **`sqlx` 0.9.0 with `sqlite-bundled`,** not `sqlite`: the full `sqlite` feature also enables loading SQLite extensions, which the server should never do.
  - **Complexity limit raised to 30** (`clippy.toml`, agreed with the human): sqlx turns on tracing's `log` feature, and each tracing macro then adds about 2 to clippy's cognitive-complexity score, so ordinary functions with two log calls failed at 15.
  - **Change from the plan:** opening the database at server startup moves to 1d, since it needs random bytes for new IDs (see 1d).

- **1d:** `storage`: `Database::integrity_check` (`integrity_check` + `foreign_key_check`) and `quick_check`. `server::startup::start` opens the database once per process (new IDs from `server::ids::new_id`, OS randomness via `getrandom` 0.4, approved), runs the integrity check, and sets `server::health` (`Starting`, `Healthy`, or `Unhealthy` with `DatabaseUnavailable` / `IntegrityCheckFailed`). The server never stops over it. `Handshake` gains `healthy` (defaults to true when missing, so API version stays 1); the Connection panel gets a **Server health** row and message. The server's data folder is `VEHICLEMANAGER_DATA_DIR`, or `dev-data/` (git-ignored) for local `dx serve`.
  - The real clock is passed in from the app (`app::logging::SystemClock`), not duplicated in `server`.
  - Tests include a deliberately corrupted file and a broken foreign key. Smoke-tested by running the server binary: the handshake reports `"healthy":true`, and a restart reopens the same database ID.

- **1e:** `domain::command`: `Command<R>` (command ID, `Stamp`, format version, `Change`), `Change` (create with all fields, update with only changed fields, delete), and the `Record` / `Patch` traits each record type implements; JSON leaves unchanged fields out. `storage::commands`: the bookkeeping queries and the `RecordWriter` trait each record's table implements. `server::commands::apply`: refuses (unhealthy, unknown format, clock more than 5 minutes ahead) before writing anything; otherwise one `BEGIN IMMEDIATE` transaction for the retry check, the server HLC, per-field last-write-wins, the record write, field stamps, tombstone, sequence number, and the applied record. Proven with a test-only note record: 11 scenario tests (including the offline-phone merge, equal-stamp tiebreak, delete, rollback on a failed write) and a property test that any order of edits, each sent twice, reaches the same state.
  - **Rule chosen (decision #043 didn't spell it out): a delete always wins.** Once a record is deleted, no create or update changes it again, even one with a newer stamp. #043 only says changes older than the tombstone are ignored. Undeleting, if ever wanted, will be its own command.
  - `applied_commands.sequence` may be empty, for commands that changed nothing (still recorded, so retries do nothing). `0001_init.sql` is unreleased, so it was edited rather than given a second migration.
  - Keeping unknown fields (#043) matters on devices, which get local storage in Phase 3; the server is always the newest version, so it knows every field.
  - Commands aren't reachable over the API yet: milestone 2 adds the first real records and the server functions that send them, with the actor and active mode.

- **1f:** `server::jobs`: one scheduler task (tokio timers) running `Job::NightlySnapshot` and `Job::QuickCheck`; each run is logged and recorded in `jobs` (last run, result, message, next run). A new database's jobs are scheduled, not run at once; a job missed while the server was off runs once at the next start. The snapshot writes `snapshot-<UTC>.sqlite` with `VACUUM INTO`, opens it read-only and integrity-checks it, then keeps the newest 7 (`storage::snapshot`). The default folder `data/snapshots` is created if missing; a folder set with `VEHICLEMANAGER_SNAPSHOT_DIR` is **never created**, so an unmounted USB disk makes the snapshot "skipped" instead of writing to the wrong disk. A failed quick check makes the server unhealthy until it's restarted. `server::startup::ServerPaths` holds the data and snapshot folders.
  - **Change from the plan: the snapshot runs at 07:00 UTC** (03:00 US Eastern daylight time, 02:00 standard), not at 03:00 in the NAS's `TZ`. Local-time scheduling needs a time-zone library, which milestone 6 needs anyway (events store their IANA zone) and which should be chosen once, there.
  - Smoke-tested with the server binary: both jobs are scheduled on a new database.
  - **Note for 1h:** the container's `/tmp` is a 16 MB tmpfs; if a large `VACUUM INTO` ever needs more temporary space, the NAS test will show it.

- **1g:** `compose.yaml` passes `VEHICLEMANAGER_SNAPSHOT_DIR` (empty by default) and has a commented-out USB mount; `.env.example` lists it, empty; the server treats an empty value as unset (Compose passes unfilled settings as empty). `docs/deploying-nas.md`: what's in `data/`; a "Database, backups, and snapshots" section (the checks, schedule, where things are, what an unhealthy server does); restoring a snapshot step by step; a rollback warning (an older build refuses a database a newer one upgraded); two troubleshooting entries. `deploy_config` test for the new variable.
  - **Change from the plan:** no `TZ` setting, since the snapshot runs at a fixed UTC time (see 1f). An existing NAS `.env` needs no change: the new setting is optional.

- **1h:** `docs/test-plans/p2m1-database-foundation.md`: 12 steps over two sessions (one overnight, for the 07:00 UTC snapshot): creation and owner, health in Diagnostics, same database ID after a restart and an update, no credential in the log, the snapshot and hourly check, a restore drill, a damaged-database drill and recovery, and (optional) a missing USB snapshot folder being skipped.
  - The damaged-database drill replaces the file with garbage (the "can't open" path) rather than damaging pages: in WAL mode a new database's data may still be in the `-wal` file, so page damage on the NAS wouldn't reliably show. Page-level corruption is covered by an automated test.
- **Passed on the NAS, 2026-10-30:** steps 1–11, with the `milestone-p2-m1-database` image. Step 12 (an unmounted USB snapshot folder; optional, another overnight run) was skipped; it's covered by the automated test `a_missing_snapshot_folder_that_was_set_explicitly_is_skipped_not_created`.
- **Raised during the run:** a maintenance tool on the NAS for restores, rollbacks, and status. Noted as idea 11 in `docs/ideas-to-discuss.md`, not scheduled.

**Choices in this plan (say if you'd rather otherwise):**
- **Runtime-checked queries, not sqlx's compile-time macros.** The macros need a database or a committed `.sqlx` cache at build time (and `sqlx-cli`); every query is instead covered by tests against a fresh temporary database (AGENTS.md §7).
- **Bundled SQLite** (compiled into the binary), so the server and later the desktop app use the same SQLite version everywhere, whatever the OS ships.
- **HLC in SQLite:** stored as `INTEGER` (signed 64-bit). The packed value stays positive until the year ~6400, and a check rejects anything else.
- **IDs in SQLite:** 16-byte `BLOB`s (half the size of text, still sorted by time with UUIDv7).
- **No real records yet:** milestone 1 builds and proves the engine with a test-only record; users and settings in milestone 2 are its first real users. That keeps this milestone about the foundation.

**Manual test plan (1h), in short:** deploy on the NAS; the database and its ID appear and survive a restart; an update keeps them; a deliberately corrupted copy makes the server report unhealthy and refuse commands; a snapshot appears at the scheduled time (or on a short test interval) and passes its check; an unwritable snapshot folder is skipped and logged.

**Choices in this plan (all approved 2026-10-30):**
- **Passwords:** at least 12 characters, no other composition rules (current NIST guidance); usernames are lowercase letters, digits, `.`, `-`, `_`, 3–32 characters, compared case-insensitively. argon2id with the library's recommended parameters, re-hashed if they change.
- **Sessions:** a web session lasts until **30 days without use** (each use extends it); signing out ends it. A disabled user's sessions end at once.
- **Desktop:** the session token is kept **in memory only**, like the test credential was (#027), so the desktop app asks you to sign in each time it starts. Saving it in the OS keychain could come later.
- **Login rate limit:** after **5 failed attempts in 15 minutes** for a username, or from one device, further attempts wait out the rest of the 15 minutes. In memory, no new dependency; it resets when the server restarts.
- **Admin mode:** entering it asks for the password again; it ends after **15 minutes** without activity, or when you switch back.
- **The setup code:** 16 characters from an unambiguous alphabet (no `0`/`O`, `1`/`I`), shown in groups of 4, e.g. `K7QM-4XRT-9PWD-H2CN`; a new one at each start until the Admin exists. Find it with `sudo docker logs vehiclemanager 2>&1 | grep -i "setup code"`.

### Milestone 5 plan: location
*Approved 2026-11-02 (every choice below) · Branch: `milestone/p2-m5-location` · Milestone PR: **#13, merged 2026-11-02** (merge commit, steps 5.0–5h; reopened after its branch was deleted before the merge) · Decisions #038, #039, #059, #060, #061*

**Reviewed against** ideas 1–18, sub-plans 01–03, and Phase 2's open questions (none), 2026-11-02:
- **Proposed: the time zone comes from the geocoder too.** GeoNames gives every city its IANA time zone (e.g. `America/New_York`), and milestone 6 needs a time zone on every event (plan §4 Event dates). Keeping it in the data file costs little now and saves a second dataset later.
- **For milestone 6, not now:** sub-plan 01 lists an event's place as "optional for cars", while the plan requires a location on every event. This is settled when sub-plan 01 is confirmed or milestone 6 is planned, whichever comes first.
- **Fits as planned:** the geocoder's data is a versioned file loaded at startup (#038), which is the shape the post-MVP reference data packs will use. - **No effect now:** ideas 2, 3, 4, 7, 10, 11, 13, 15–18; sub-plan 03.

**Choices** (approved 2026-11-02, #059):
1. **The geocoder: a small lookup of our own, with only what's needed and no new runtime dependency, and a proper spatial index so lookups stay fast.**
   - `reverse_geocoder` compiles its city list into the program, which #038 rules out (the data must be a file that can be updated without a new build). It also covers cities only, not states and countries.
   - The `geo` crate is large for the three things needed: the nearest city (a grid index), which country and state contain a point (point-in-polygon, with bounding boxes first), and the nearest boundary when none does.
   - Our own code is a few hundred lines and fully tested.
   - **Spatial index (asked for):** candidates come from the GeoPackage's R-tree (bounding boxes), never a scan of every city or boundary.
2. **How the data file is made: during the image build, from pinned downloads checked by SHA-256, never committed.**
   - A short-lived Dockerfile stage, from the official GDAL image pinned to a version and digest, downloads exact versions of GeoNames `cities500` and Natural Earth's 1:10m countries and states, refuses them unless their SHA-256 matches, and runs `ogr2ogr` to write `geodata-<version>.gpkg`.
   - **Cities: `cities500`** (places of 500+ people), changed from #038's `cities1000` for accuracy in small places (asked for; the raw file is about 41 MB instead of 32 MB).
   - The runtime image copies only that file, beside the server. GDAL never reaches the NAS.
   - For development, `scripts/geodata/fetch.sh` runs the same steps with `docker run --rm` into a git-ignored folder. Downloads are untrusted until their checksum matches (AGENTS.md).
3. **The file format: GeoPackage (`.gpkg`),** the OGC standard (asked for: a common format where possible).
   - It's a SQLite database, so the server reads it **read-only through `sqlx`** (no new dependency); our bundled SQLite has the R-tree module.
   - Three layers (countries, states and provinces, cities with their time zones), each with its R-tree index, plus a metadata table: the data version, sources, checksums, and licences.
   - QGIS and GDAL open it, so the data can be checked by eye.
   - Compared and not chosen: SpatiaLite (a native extension we'd have to ship), FlatGeobuf (one file per layer, two new crates), GeoJSON (no index; used only as a source), Shapefile, GeoParquet, PMTiles (map tiles, for #039 later).
4. **Saved places are each person's own** (changed from plan §3's "shared"), **and they're aliases:**
   - Each place has a name, coordinates, a radius, and its city, state, and country.
   - Choosing one, or being inside its radius, **copies** its name and location into the event. Editing or removing the place later never changes past events.
   - Each person adds, edits, and removes their own. No role is needed.
   - **Default radius 150 m**, adjustable from 25 m to 2 km.
   - **Typed places are first-class** (asked for, 2026-11-02): the city and state or province are free text, never checked against GeoNames, so an unincorporated community or a military base that GeoNames doesn't list can be entered as it's known. Only the country must be a real ISO code. The geocoder's suggestion only pre-fills the fields.
   - **Inside a saved place, its own city, state, and country win** over the geocoder's suggestion: the alias is what the person chose (milestone 6's event forms follow the same rule).
5. **The Places screen:** under Manage, with **SVG options first**. Since places are each person's own, everyone sees it. A place can be added three ways:
   - **Use my location:** the browser's location, on phones.
   - **Typed coordinates:** for desktops without GPS, and for testing a coastal point.
   - **Editing the city, state, and country** the geocoder suggested.
6. **Attribution:** an **About** section on the Diagnostics screen, with the app version, the geocoder data version, and "Contains GeoNames data (CC BY 4.0)" and Natural Earth's credit (#038). There's no separate About screen yet.
7. **If the data file is missing or broken,** the server still starts. Places and events then fall back to saved places and typed city, state, and country, and an **Admin message** says that place lookup is unavailable (#050).

   - **Chosen: B** (decision #065). Files never change, so the folder needs no snapshotting of its own; the integrity check verifies each file against its hash.
2. **HEIC.** #036 converts HEIC to JPEG. Decoding HEIC needs `libheif` (a C library): easy in the Docker image, an extra install for desktop builds. iPhone Safari usually hands the browser a JPEG already.
   - **Chosen:** the browser makes the JPEG (as #036 says, resizing before upload), so HEIC only matters for a **kept original**, which is stored as is and never decoded. The server refuses a HEIC *photo* it would have to convert, with a message. No `libheif` now.
3. **PDF page count and first-page thumbnail (#037).** The server can count pages with a small pure-Rust PDF reader (e.g. `lopdf`), but can't draw a page without a renderer such as pdfium.
   - **Chosen:** the app draws the first-page thumbnail with the bundled pdf.js before upload; the server checks it's a real PDF and counts the pages itself. A PDF without a thumbnail shows a plain document icon.
4. **What can carry attachments.** The plan says events, squawks, and vehicles; M7 deferred "squawks and tasks".
   - **Chosen:** events (any kind), squawks, vehicles, and official documents; **tasks** too, as a small step (a receipt on the brake job). Owners are stored as a kind and an ID, so milestone 9's acquisition and disposal records can use them.
5. **License plates** (milestone 8's open questions):
   - **Its own record or part of the registration?** **Chosen: its own record** on the vehicle (decision #066): an issuing authority (a US state or Canadian province from a list, or a country, or other text), a number, and from / until dates. The current one shows in the header; earlier ones are its history. A registration **links to** the plate it's for, and renewing it updates that plate's expiration.
   - **Other identifiers** (a boat's state registration number): **chosen: plates only now**; the record is general enough to add more kinds later.
   - **Existing plates:** a migration moves each `plate` identifier into the first plate record with **no authority yet**, and the vehicle's page asks for one.
6. **Attachments on finished events.** Finished and finalized events are locked (#034), and a later signature would hash their attachments (sub-plan 01).
   - **Chosen:** attachments are part of a draft; after it's finished, adding or removing one is a **correction** (6h), like any other change. Squawks, vehicles, and documents take attachments any time.
7. **Who adds and removes them.** **Chosen:** anyone who may change the owner (a Driver on a fuel-up, a Maintainer on a job, a Driver on a squawk they may edit); **official documents** need a Maintainer; removing is a soft delete (#043), and a file is erased only when nothing points to it any more.
8. **Size picker defaults** (#036: profiles set the default per event type). **Chosen:** Small on fuel-ups and readings, Medium everywhere else, Large never by default.

**Choices from the plan** (no question needed):
- Photos: Small 1280 / Medium 2560 / Large 4096 px JPEG (quality 85), upright, 400 px thumbnail, 25 MB limit, never enlarged; metadata (time, GPS, camera) read in the browser before resizing and kept as fields; originals kept only by Maintainers and Admins, off server-wide by an Admin (#036).
- PDFs: 50 MB, checked and page-counted by the server, shown with the bundled **pdf.js** on web and desktop, with Download (#037).
- Official documents: type (from the profile, or custom), number, issuer, issued and optional expiry dates, scans, notes; **renewing** makes a new record that supersedes the old one (current, expired, superseded); the Documents tab shows the current ones first.
- Uploads go under `/api/v1/files` (behind the auth layer); only that route's body limit is raised.

### Milestone 9 plan: asset lifecycle, reference documents, and showing only what each person may use
*Approved 2026-11-05 · ✅ Done 2026-11-06 (all 40 test steps passed) · Branch: `milestone/p2-m9-lifecycle` · Milestone PR: into `dev` · Decisions #034, #040, #050, #051, #052, #057, #067, #068, #069*

**Goal:** a vehicle's whole life is on record: when and how it was **acquired**, when it went **out for service** and came **back**, and when and how it was **disposed of** (after which its records stay, read-only). Recalls and bulletins can be entered as **reference documents** that requirements link to, with **one-time** compliance (done once, then closed) beside recurring, and an **applicability** decision. And before `v0.2.0`, when the rest of the household starts using the app, **each person sees only what they may use**.

**Questions for the human, and the answers** (2026-11-05: 1 and 3–7 as recommended; 2 and 8 changed, as shown):
1. **Lifecycle events: four new kinds of event** on a vehicle's Timeline, each with attachments, following the normal finalizing rules (#034):
   - **Acquired:** date, from whom (seller, dealer, manufacturer), price and currency, condition notes, the starting readings.
   - **Sent out:** date, the shop, a work order number, the expected return date, shipping and tracking, the estimated cost. Sets the status to **Out for service**.
   - **Returned:** date, the final cost, notes (the return paperwork attached). Sets it back to what it was before (usually In service).
   - **Disposed:** how (sold, traded in, scrapped, given away, returned to the vendor, lost or stolen, other), date, to whom, price, the final readings, notes. Sets the status to **Disposed**.
   - **Recommended:** these four, from **+ Log** (Sent out and Returned for a Maintainer; Acquired and Disposed for the vehicle's Admin, since they change what the household owns). The shop's own work while it's out is an ordinary maintenance job, **performed by** the shop.
2. **A disposed vehicle is read-only.** **Recommended:** no new events, squawks, documents, or changes once its disposal is finished; it stays viewable and in reports. To undo a mistaken disposal, the Admin **corrects** the disposal event (6h) to "not disposed", or deletes it while it's a draft.
   - **Answer:** as recommended, except that **corrections are still allowed** on a disposed vehicle's finished records (its events, including the disposal itself); only **new** events, squawks, and documents are refused.
3. **Acquired for vehicles already in the app.** **Recommended:** one per vehicle, added any time from **+ Log** (most of the household's vehicles were bought long ago); the add-vehicle form doesn't ask for it now.
4. **An overdue return.** **Recommended:** a day after the expected return date with no Returned event, a message (#050) for the vehicle's Maintainers and whoever sent it out, opening the Sent out event.
5. **Reference documents** (recalls, bulletins), shared across the household: type and issuing authority (e.g. NHTSA, the maker), reference numbers (several), title, description, remedy, issued and effective dates, a revision, applicability as written (text), a URL, and attachments.
   - **Recommended:** a Maintainer adds one from a vehicle's **Maintenance › Set up** ("+ Recall or bulletin"), which makes the record and that vehicle's requirement for it in one go; another vehicle can link the same record ("+ Requirement from a recall or bulletin"). A household-wide list of them can wait (no new sidebar item now).
6. **Compliance modes and applicability.** **Recommended:** every requirement gets a **mode**, **Recurring** (today's, with its rules) or **One-time** (done once: the first finished task that does it **closes** it, "Complied on …"); and an **applicability**: Applies (the default), **Not applicable** (a reason required; it drops out of the schedule but stays listed), or **Under review**. Status is worked out (open, complied, active, not applicable), not stored. The other two modes are Phase 5.
7. **Users and Groups while the Admin isn't in Admin mode** (the open question from 2026-11-02). Today they show and say "Switch to Admin mode". **Recommended:** **hide** them outside Admin mode, like every other Admin-only screen, with the mode menu itself as the way in.
8. **The sweep** (show only what each person may use). **Recommended:** walk every screen as each role (Viewer, Driver, Maintainer, Admin in each mode) and remove any button, menu item, or field that would only be refused; Settings' You / Household picker only for the household's Admin in Admin mode; the vehicle page's "view only" note stays. A short report of what changed goes in the notes, and the test plan walks the same screens as Sam.
   - **Answer:** more general: **a screen, tab, button, menu item, or field shows only if the person's role, capped by their current mode, allows it** (on that vehicle, where it's per vehicle), for every role and mode, not just the Admin's. Anything refused is hidden rather than shown and refused. The server still checks everything.

**Later questions, and the answers** (2026-11-05, while planning 9b and 9c):
9. **The `events` rebuild (9c):** `events.kind`'s check lists only the four everyday kinds, so migration 0015 rebuilds the table the way SQLite documents it (`-- no-transaction`, foreign keys off, copy, swap, `foreign_key_check`), tested on a filled database. **Answer:** approved, with the lifecycle details in their own `lifecycle_details` table (one row per lifecycle event).
10. **A recall's PDF:** every attachment belongs to one vehicle today, and the owners are fixed by a check. **Answer:** 0015 also **rebuilds `attachments`**: a new `reference` owner with no vehicle; anyone who can see a vehicle linked to the reference document sees its attachments.
11. **Who edits a shared reference document:** **Answer:** a Maintainer of **every** vehicle that links it, or the household's Admin in Admin mode. Anyone who can see one linked vehicle can read it.
12. **Its types:** **Answer:** the plan's list: recall, technical service bulletin, service bulletin, manufacturer schedule, other (airworthiness directives come with aircraft).

**Choices from the plan** (no question needed):
